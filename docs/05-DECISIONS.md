# 05 — Decisions I took on your behalf

*You asked me to answer my own open questions with the best suggested answer and to keep going without stopping. This is that record. Every one of these is a real, reversible decision with a stated rationale, and the code already reflects it. Say the word on any line and I reverse it — the cost is a refactor, not a re-think.*

| # | Question I would have asked | Decision taken | Why this is the best default |
| --- | --- | --- | --- |
| 1 | One insurer, a group, or SaaS sold to many insurers? | **Multi-tenant capable, pilot shaped as one operator group with two legal entities** (conventional + takaful window). Tenancy is a first-class dimension; the demo runs a single group. | Multi-tenant costs nothing to design in and everything to retrofit. Starting with a group exercises the hardest finance path (two entities, one consolidation) immediately. |
| 2 | Which country pack first? | **UAE (CBUAE-flavoured) first, Malaysia (BNM) second.** Both are implemented as data with their differences (surplus-to-savers restrictions, cooling-off, need-analysis triggers). | You work in Dubai, the takaful rules are strictest-but-clearest in the UAE, and Malaysia is where takaful operations are most mature — it proves the pack architecture is genuinely portable. |
| 3 | Are we the fund manager or do we consume third-party NAVs? | **Both: the platform runs its own NAV engine, and accepts administrator/vendor files.** The seeded world prices funds from an administrator-style file. | Owning the engine is the ILAS-beating claim; accepting external NAVs is what every real operator needs on day one. |
| 4 | Payment rails and wallet vs arrears for daily/PAYG cover? | **Prepaid wallet first, arrears as a product option.** Cover suspends rather than part-charging into a negative balance. | Prepaid removes credit risk from micro-duration cover, which is the only way insurers will underwrite a 12.50 AED day of motor cover profitably. |
| 5 | Takaful first, or conventional-with-takaful-window first? | **Conventional + takaful window in one tenant first**, with full pool segregation, because that is the harder problem and it subsumes the standalone case. | A window that stays pure can be extended to a standalone entity trivially; the reverse is not true. |
| 6 | Legacy book migration (ILAS or another core)? | **No migration in v1**; the ingestion fabric is built to absorb any shape of file, which is what a migration actually needs before it needs a mapping tool. | You have no book to move today. Building migration tooling before the target schema settles wastes the work. |
| 7 | Stack? | **TypeScript end-to-end (core, server, console), Postgres-shaped domain model, event-ready outbox.** No framework lock-in; the API server is plain Node so it runs anywhere. | One language maximises agent throughput and keeps the domain readable by humans reviewing regulated logic. |
| 8 | How far can AI agents go? | **Agents propose; humans dispose.** Payouts above limits, final pricing, Shariah rulings, actuarial certification, surplus distribution and any ledger override are on a prohibited list the runtime enforces. | This is exactly where regulators are converging, and it is also the difference between a tool that gets approved and one that does not. |
| 9 | Multi-bilingual scope? | **English and Arabic first-class (with RTL-ready labels), then Malay/Indonesian, Urdu, French, Chinese in the backlog.** Data translation is kept separate from label translation. | Arabic is mandatory for the UAE; keeping the two translation concerns apart is what makes a scanned Arabic name safe to display in English. |
| 10 | What does "finished" mean? | **The phase gates in `04-PHASES.md`, evidenced by the money proof and the regulatory journeys** — not a date. | The fleet works a chunk at a time; pretending to know a finish date would be theatre. |
| 17 | Where do the numbers on a regulatory return come from? | **Straight from the register and the ledger, with a control per schedule that names the account it compares against, and a refusal to issue when any control disagrees.** A difference can be accepted, but only by a named approver, only with a sentence saying why, and the acceptance travels on the face of the extract. | A return assembled by hand from a spreadsheet is a return nobody can re-derive. Tying each schedule to an account means the reconciliation a regulator asks for already exists, and the refusal is what makes the control real rather than decorative. |
| 18 | What does an extract say about what it does not know? | **It says so, in a limitations block**: no IBNR, no discounting, no unexpired premium on annual business, no large-loss smoothing. The paid and reserved facts are given, and the arithmetic stops where the actuary's own model begins. | An actuary can work with an honest gap. They cannot work with an invented figure, and a return that quietly fills one is the most expensive kind of wrong. |
| 19 | Can an issued return be edited? | **Never.** Content is fingerprinted; issuing identical content again returns the same extract, and different content for the same period creates a new version that supersedes the old one — with a reason of at least a sentence, and an earlier reporting date cannot replace a later one. The old version stays and is reported as no longer reproducing. | Supervisory returns get corrected. The question is only whether the correction is visible. Keeping the superseded version and stating why is what makes the correction auditable. |
| 20 | How does a treaty bordereau stay consistent with the return? | **Both are built from the same register and cross-checked against the same ledger accounts**, and the bordereau carries a closing balance per counterparty. | A counterparty query should land on one number. Three numbers — the desk's, finance's and the reinsurer's — is how a settlement takes six months. |
| 21 | How are country rules enforced — prose or code? | **Rules are records, not paragraphs.** Each rule carries its instrument, its clause, its plain-English requirement, the same requirement in Arabic, the evidence an examiner asks for, and what a breach does. The engine evaluates them on every placement. | A rule that lives in a policy manual is enforced by whoever remembers it. A rule that lives in the placement path is enforced by the system, and the decision it produces is the evidence. The Arabic is not decoration: the desk that has to apply the rule reads Arabic, and a rule that only reads well in English is half-enforced. |
| 22 | What happens when a fact cannot be shown at all? | **It escalates, whatever the rule's severity.** A breach either refuses the placement or is held for a named human who may accept it in writing; a fact that is missing — no rating on file, no certificate, no Shariah approval — is always held, because silence must never be allowed to look like compliance. | The dangerous state is not the known breach; it is the placement that sails through because nobody checked. Making 'unproven' its own answer means the system cannot mistake an absence for a pass. |
| 23 | Which UAE instruments does the reinsurance rule book cite? | **Federal Decree-Law No. 48 of 2023 (Arts 42, 50, 64) as carried forward by Federal Decree-Law No. 6 of 2025 (Art 82), the CBUAE reinsurance regulations (Arts 18, 31, 38, 39) and the financial regulations' admissibility of recoverables.** Citation and instrument version sit on every rule. | The 2025 law consolidated the insurance regime into the CBUAE mandate with a transition to September 2026, so both instruments are live in the period the demo runs in. Pinning the citation to the rule means an examiner can check the wording, and a moved clause shows up as a finding to update rather than as silence. |
| 24 | Does the rule book claim to read the rulebook for you? | **No, and it says so on every statement.** It holds the rules the carrier has decided to enforce, each with its citation; it does not re-read the source text, and a citation that has moved is a finding to correct. | A compliance engine that implies it tracks the rulebook is worse than one that admits its version: the first breeds false confidence, the second gets reviewed. |
| 25 | Is a mandated disclaimer a paragraph in code? | **It is a record with both languages and the instrument that requires it.** The generator composes the letter around them and refuses to produce one that is missing a paragraph its template requires; a paragraph that does not belong on that document type is refused too. | Marketing can rewrite a brochure. Nobody may quietly drop the sentence that says the cover was placed with a licensed company — and a generator that cannot drop it is the only kind that guarantees it. |
| 26 | What may a rename change? | **A label, never a mandated paragraph.** The takaful window's letters say *contribution* for the same field the conventional book calls *premium*, through the same label registry the screens read; the segregation paragraph is byte-identical in both documents. | Renaming is how one ERP serves a takaful entity under its own regulator's vocabulary. If a rename could reach the disclaimers, the window could rename its way out of the regulation. |
| 27 | Which scope decides what a letter contains? | **The template, per scope.** A conventional treaty note states a premium and carries no segregation paragraph; the window's states a contribution and carries it. The paragraph set and the field set belong to the template, so a new scope is a data change. | Takaful wording differs structurally, not cosmetically. Encoding that in the template means the difference is reviewable in one place instead of buried in an if-statement in a letter writer. |
| 28 | What does a generated letter say about itself? | **The pack version that produced it, the accounts it ties to, and whether it still reproduces.** Generating identical content returns the letter already on file; a moved figure supersedes it with a changes summary and keeps the earlier version. | A wording review happens under filed documents. Recording the pack version is what lets a reviewer see which letters were written under the old wording without reading every one. |
| 29 | When is a return actually filed? | **When the supervisor says so.** The pack goes out through a named channel with its cover letter and its controls; the filing stays outstanding, and the log reports it as outstanding, until an acknowledgement with the supervisor's own reference is recorded against it. | A submission register that treats sending as filing is how a missed deadline is discovered by the regulator rather than by us. The outstanding list is the control. |
| 30 | Is the deadline the first day or the last? | **The last.** The window opens when the period ends and closes at the deadline plus its grace; filing the day after the period closes is normal and on time. Filing for a period that is still running is refused outright. | Treating the deadline as the opening day would block the ordinary case, and a control that misfires in the ordinary case gets switched off. |
| 31 | What happens when a filed return has to be corrected? | **The corrected return supersedes the earlier filing** — the correction is filed against it, the earlier filing is marked superseded, and a return for a period that already has one cannot be filed beside it. A filing that was rejected stays rejected: a correction does not rewrite a rejection. | Corrections are normal and must be visible; a second filing sitting unlinked beside the first is how a period ends up with two returns and no answer to which is the filed one. |
| 32 | Can a return be filed after the books have moved? | **No: the register recomputes the return from the books before it accepts the pack.** A return that no longer reproduces is refused, and the corrected return is issued and filed instead. | The filed return and the filed figures have to be the same thing. Rechecking at the moment of filing is the only moment that matters. |
| 33 | What does a register have to keep to be restorable? | **The facts each record was made from.** A rule decision is stored with the placement it was decided on; a letter with the facts it was generated from. Restoring therefore replays the records through the engines that made them and checks the answers match — a restore is a proof, not a copy. | A record that can be quoted but not re-derived cannot be defended. Keeping the facts costs a few kilobytes and turns "we think this is what it said" into "run it and see". |
| 34 | What happens when a restore meets a world that is already partly there? | **Nothing is duplicated.** A decision already in the register is not taken twice and a filing already logged is not filed again; the restore fills the gaps and reports what it found. | A restore that double-counts is worse than one that fails loudly, because the second run is the one nobody watches. Idempotency is the property that makes a restore safe to run at any time. |
| 35 | How does a snapshot prove that nothing was dropped? | **A hash-chained outbox.** Every record is written to a log whose entries each carry the hash of the entry before them; a gap, a reorder or an edited entry breaks the chain and the restore says which entry broke it. | A fingerprint proves a payload is intact; it cannot prove the payload is complete. The chain is what distinguishes "these are all the records" from "these are the records that survived". |
| 36 | Is this a database? | **No, and it says so on every snapshot.** There is no transactional write, no concurrent-reader isolation and no incremental streaming of the outbox; those belong to the Postgres and outbox chunks this shape is built to hold. | Claiming a file-backed snapshot is a database is how teams discover the difference during an audit. Naming the gap is what makes the shape reviewable. |
| 37 | What is a return re-proved against? | **The books as far as it could see.** Every record carries the mark of how many journals were in the books when it was made, and the restore advances the books to that mark before replaying it. | A corrected return filed after a catastrophe recovery was prepared with the recovery in the books; the return it superseded was prepared without it. Replaying both against one set of end-of-day books refuses the first — and the restore would then be measuring history with the wrong books and calling the answer a failure. |
| 38 | What happens when a return is made from something the store does not carry? | **The restore names that return and says why, and does not call the restore good.** Loading the inputs a return is made from — a catastrophe recovery, a claim — is its own chunk. | A store that reports "restored" while its records cannot be re-proved is the failure this whole register exists to prevent. Naming the one record it could not re-prove is the honest version, and it is also the work order for the next chunk. |
| 39 | What does the world's id sequence owe a restore? | **The same world built twice comes out the same, ids included.** The sequences that name journals and takaful documents are restarted at the top of `buildWorld()`. | The drill builds a second world and compares it with the first record by record. If the same journal is `TKF-J-000023` in one world and `TKF-J-000031` in the other, the comparison is between two different worlds and proves nothing. |
| 40 | What does the store have to keep besides the rows? | **The actions the registers took.** A cession, a catastrophe recovery, a reinstatement, a deposit settled, a reserve moved: each is a decision somebody took, it belongs to a register, and it posted a journal. The register records it with its own inputs and the journal it posted, and a restore takes it again through the same register. | A store that keeps only the end state can put rows back but cannot reproduce them. The first drill run against a world that had traded found exactly that: a return prepared after a catastrophe recovery could not be re-proved, because the recovery itself was never kept. |
| 41 | In what order does a restore put things back? | **The order the world lived them.** Actions and returns go on one timeline — an action sits at the journal it posted, a return at the point in the books where it was issued — and the books are advanced to each mark before the record is replayed. Where an action and a return share a mark, the action comes first. | Two passes, actions then returns, hands a Monday return a register that has already seen Tuesday, so it refuses — and the restore would be blaming the return for being right at the time. The order is not a detail of the implementation; it is the difference between a proof and a plausible-looking failure. |
| 42 | What is the restore's strongest check? | **The books, journal for journal.** After the replay, every journal in the rebuilt books is compared with the snapshot's: the same id, the same source, the same postings, the same amounts. Balances agreeing is not enough. | Two different sets of entries can arrive at the same totals — through a different account, a different split, a different fee. A restore that only compares balances will call that a success, and the drift stays in the books for good. |
| 12 | How does a customer actually open the demo when the sandbox preview is gated? | **Publish the demo as static pages** (`demo/site/index.html` + the offline console + the gallery) and hand over a plain HTTPS link; the sandbox preview URL is treated as a bonus, never as the route. The Pages workflow assembles the site, and a raw-code host (raw.githack) serves the same committed files immediately. | An access token sitting on a proxy is not something a customer can be asked to work around, and a video is not the product. A committed, self-contained page opens from any browser, in any country, with no port, tunnel, token or install — and the offline console is the real application, so what they test is what we ship. |
| 13 | What must a reinsurer's security actually cover, and how much of it? | **Every recovery still outstanding, in full, plus a treaty-specific margin (bps of ceded premium written) for premium still unearned.** A treaty may set no margin — plenty do — but a recoverable is never optional: if the counterparty will not pay, the security is the only thing that pays. | The recoverable is the money we have already committed to a claim; a premium margin prices the run-off risk on top of it. Making the margin per-treaty keeps a facultative placement honest and lets a catastrophe treaty be secured at 40% of premium while a quiet surplus treaty carries none. |
| 14 | Is a letter of credit "held" money? | **Counted in the cover, disclosed, never posted.** Cash and premium withheld move the books — restricted cash against a returnable security liability, or the payable down — while a letter of credit and a bank guarantee are recorded with their reference and expiry and reported as off balance sheet. | Pretending an unspent promise is cash is how a balance sheet flatters itself. The security statement shows both, so the reader sees the cover *and* knows which part of it could not be spent tomorrow morning. |
| 15 | Interest on cash a reinsurer has posted? | **Credited to the counterparty on a conventional treaty, refused outright under a retakaful one** — the refusal is a sentence in the engine, not a note in a policy. | Interest on cash posted for a participant's risk is riba, and a window that posts it and "fixes it later" has already broken segregation. On the conventional side the interest is theirs, so it is carried as more of what we owe them and the reconciliation proves both halves. |
| 16 | May a release of security leave an exposure uncovered? | **Only with a name against it.** The engine refuses a release that would create a shortfall unless an approver is named; when one is, the release is posted, the waiver is recorded and a REINS-066 finding reports it for as long as it stands. | Treasury sometimes must take security back, and a system that simply forbids it gets worked around. A named approver and a standing finding is what a regulator can actually inspect. |
| 43 | Who decides the order between two things a restart has to put back — the books or the registers? | **The registers keep their own clock and it has the last word.** Every register takes a ticket from one shared clock as it records an action; every return and every filing remembers the ticket count at the moment it was issued. The restore sorts on the book position first, then on the clock, and an action comes before a return when both agree. Schema v4; a v3 payload migrates with an absent ticket read as unknown, which sorts the record after the actions at the same book position — all v3 could truthfully say. | An action that posts no journal — a claim registered, a triage, an approval — sits at the same book position as everything before it, so the books cannot order it against a return issued around it, and the rebuild guessed. That guess is what made one seeded exhibit (`RI-EX-ALK-CONV-00002`) come back with a different fingerprint after a full console session. A clock shared by every register costs one integer per action and turns the guess into a fact. |
| 44 | What is a reported record's identity, and what is a store allowed to refuse? | **Book, register and id — all three.** The conventional and takaful returns both number from `SUB-000001`, so the register and the id together are not a name; the book is folded into the entry and into the hash that covers it, and a record's presence is looked up by all three. The store refuses a duplicate rather than chaining it twice, refuses a record with no book, no name or no timestamp, and refuses an append with nothing in it. | A log that holds one name twice is a log whose reader is guessing, and the reader here is a supervisor: two returns filed on the same day must not be one entry. The refusals are the same idea from the other side — a record that cannot be named, placed in a book or timed cannot be found again, and finding it again is the whole point of a log. |
| 45 | How much of the outbox has to be proved on every read? | **The tail, from the last checkpoint — with the checkpoint's own hash still standing behind it.** Every 100 entries the store records the hash at that point; a reader proves everything after it without walking the chain again, and the drill still walks the whole chain from genesis once, because a checkpoint is only worth what the chain behind it is worth. | Walking a day's worth of entries to answer one question is work that grows with the business, and a proof nobody runs is not a proof. The checkpoint makes the cheap answer honest — it fails loudly if the entry it names has been rewritten — and the drill keeps the expensive answer, which is the one a regulator asks for. |
| 46 | Where does the reporting log live, and what is durable? | **In the process, and the registers are what is durable.** The store holds the outbox as versions with checkpoints and serves them over HTTP — a reader catches up from an entry number and gets the head hash with the page — but it is the registers, sealed into the canonical snapshot, that a restart restores. The store's job is to prove nothing the registers reported was dropped while the day was being worked, and the drill proves the same property from the snapshot side. | Persisting the log on disk as well would give two answers to one question, and the honest one is the registers'. A reader who wants the log after a restart rebuilds it from the registers — the same walk, `outboxItems`, one code path — and gets byte-identical hashes, which the store's first test asserts. |
| 47 | How much testing has to pass before the fleet calls a capability done? | **Every test file the module maps to.** A capability that spans the books and the reporting log is not proved by the books alone, so `implemented.json` maps a module to a list of files and the fleet runs each of them; one red file returns the claim as blocked. The rest of the gate is unchanged — the capability has to match something built, and the evidence files have to exist. | The alternative was measured, not imagined: with one file per module the fleet could claim a two-area capability while the second area's file was red. The fleet's numbers are only worth what its gate is worth, and the user's standing rule is that every claimed chunk is actually built and tested. |
| 48 | How does a restore put back a record it may already hold — by content or by identity? | **By identity, always.** A rule decision is matched by its id: the restore compares what the target already holds under that id and replays the rest in the order they were taken, refusing an id that comes back different. Content is compared *within* the match, never used to find it. | Two decisions taken the same day on the same facts are two records — the console really did run the same check twice. Matching by content folded them into one and the rebuilt log came back short; matching by identity keeps the log as long as the day was. The same rule already governs filings (book + register + id) and it now governs decisions. |
| 49 | May the log be *grown*, or must it be rebuilt when a new record belongs in the middle? | **Rebuilt, and it says so.** The store checks that the log it holds is a prefix of the walk over the registers; a record created later that belongs before entries already logged forces a rebuild in the records' own order as a new version — never an appended entry in the wrong place. An entry that did not move keeps its hash, older versions stay readable, and the write report carries `rebased` with a sentence naming the entry and the two records. | A chain proves order, and an order that disagrees with the records is a log that lies about the day. Rebuilding is safe precisely because the log is derived: the registers are the durable artefact, the chain is deterministic, and a reader who opened version 4 keeps the log as it was. Growing the log was the obvious implementation and it was wrong for exactly one afternoon's session: a return issued late, sitting before decisions taken early. |
